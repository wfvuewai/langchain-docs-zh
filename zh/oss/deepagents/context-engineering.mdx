## 概述

上下文工程是设计和优化代理系统提示、工具描述和上下文的实践。对于两到三个提示来说不成问题的东西，对于复杂的深度代理设置来说可能会出问题。

本页面涵盖了减少 LLM 错误和改善代理输出的模式。

## 系统提示设计

系统提示定义了代理的整体行为。一个结构良好的系统提示可以决定成功部署和令牌被浪费的区别。

### 结构

提示结构应遵循逻辑顺序，引导代理从建立身份到执行再到约束。

1. **身份设定**：简要定义角色和总体目标。
2. **核心责任**：代理应处理的关键任务。
3. **执行指南**：关于使用工具和在某些情况下如何行动的具体说明。
4. **约束和边界**：限制和护栏。
5. **输出规范**：期望的结果格式。

### 风格

为了使系统提示与 Deep Agents 和其他编排系统良好配合：

- **使用清晰、直接的语言**。避免模糊的表述或过多的形容词。
- **将冗长的指令分解为短块**。使用标题、编号列表或有重点的段落。
- **对约束使用否定式表述**：在输出规范之前，明确说明代理不应做什么。
- **具体说明工具**：如果某个工具是单次调用，请提及。如果应该并行调用工具，也要提及。

### 反模式

| 反模式 | 为什么它不起作用 | 更好的做法 |
|---------|------------|-------------|
| "做一个好助手" | 模糊，没有约束。 | 具体说明领域和限制。 |
| 8000 字的提示 | 模型迷失在文本中；核心指令被稀释。 | 将提示拆分为独立的部分。 |
| 代理工具描述含糊不清 | 代理调用错误的工具或遗漏参数。 | 描述每个工具何时使用。 |
| 没有指定输出格式 | 每次运行格式不一致。 | 使用结构化输出或格式约束。 |
| 列出所有事情同时进行 | 代理可能不按顺序执行。 | 对步骤进行编号或指定优先级。 |

## 提示链

提示链超越了单个系统提示，创建了细粒度的提示块，作为代理决策流的一部分动态组合。关于组合提示的主题，请参见[提示组合](/oss/deepagents/prompt-composition)。

对于深度代理，系统提示由多个元素组成：

- **分块提示**不是单一的、庞大的提示，而是将提示分解为多个块，每个块都有自己的特定目标。
- **条件包含**可以是动态的——不同的上下文触发不同的提示块。

## 工具描述工程

一个定义明确的工具描述与系统提示同样重要。在 Deep Agents 中，工具是代理如何与外部系统交互的方式。工具描述的明确程度决定了这些交互的成功与否。

### 最佳实践

1. **描述**应该清楚说明工具何时以及为何被调用。
2. **参数**应该精确，具有正确的类型和清晰的描述。
3. **避免参数描述中的歧义**。说"要搜索的查询"可能会产生歧义；说"要在搜索引擎中搜索的关键词或短语"更清晰。

## 上下文管理

上下文管理是关于构建输入上下文以最小化 LLM 干扰的。

### 上下文清洁

深度代理的一个常见问题是不相关的上下文渗入系统提示。以下是一些使其保持清洁的方法：

1. **为每次调用使用唯一、隔离的线程**。LangGraph 支持线程级持久化，你可以为每个独立的对话或任务创建一个新线程。
2. **隔离子代理工具**。将嘈杂的工作委派给子代理，以便主代理上下文不受影响。
3. **修剪历史**。如果对话变得太长，总结较旧的消息，并使用受支持的消息修剪技术。Deep Agents 支持自动的令牌使用管理。
4. **使用较小的输出**。指示工具返回较小的结果，而不是在上下文上倾倒。指示子代理始终返回摘要。
